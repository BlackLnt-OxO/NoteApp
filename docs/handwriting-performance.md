# 手写与笔画擦除性能分析

> 后续复测仍发现整笔擦除的偶发卡顿。新审计已复现冷缓存重建和 64 MiB 缓存循环淘汰的长帧；此前热缓存数据不代表这些场景。详见 [笔画擦除架构对照与复现](stroke-eraser-architecture.md)。

验证日期：2026-09-11。复现场景：当前项目开发版，默认标记笔，笔尖一直按住、连续左右往返；另有密集笔画下的整笔擦除延迟。

## 为什么上一轮仍然卡

阅读了 README、CLAUDE.md、UI_CODE_REFERENCE.md，以及无限画布、PDF 标注、笔刷、状态与保存实现。后两份文档主要描述较早的便签/截图功能；当前手写结构以实际代码为准。

上一轮减少了 pointermove 的 React 更新、推迟了落笔期间的自动保存，并将擦除后的整瓦片重绘缩小到受影响区域。这些修改保留，但没有覆盖两个关键负载：

1. **同一笔持续往返。** `drawAnnotatedStroke` 以前每一帧都对全部历史点重新平滑、计算压感宽度、重采样，再把大量小四边形和圆盘加入同一路径，执行一次填充与羽化。左右反复覆盖时，既有持续增长的 JavaScript 工作量，也有高度重叠路径的光栅化开销；后者可以远超线性增长。仅合并输入事件或限制 React 更新不能解决它。
2. **许多笔画真正重叠。** 上一轮局部修复可以跳过远处笔画，但如果剩余笔画都与删除区域相交，仍须重新计算、填充和羽化每条幸存笔画。先前“同瓦片、笔画分散”的测试没有覆盖这种情况。

此外，擦除按下时仍重建空间网格，点击仍可能遍历整个笔画集合，长笔画命中测试也扫描全部原始线段。

## 已实现的修复

### 长笔画增量绘制

新增 `StreamingInkStroke.ts`，两个编辑器创建的新标记笔/钢笔笔画均使用它；后续已补齐铅笔笔芯与纹理的增量路径，详见下方铅笔补充记录：

- 已处理的笔画覆盖区域保存为 128×128 世界单位、3 倍采样的小块，每次只处理新增采样点及受影响的小块。原始矢量采样仍保留用于存储、撤销、移动和重新加载。
- 历史采样只烘焙一次；最后一个点作为可替换的实时笔尖，后续输入到来后再平滑并烘焙，避免错误地将临时笔尖永久留在墨迹中。
- 新线段的几何数量有界，不再沿已经笔直的线段重复插入大量 1 像素圆盘。
- 先累计不透明的覆盖蒙版，再统一应用颜色、透明度和羽化。因此同一条 50% 透明笔画反复覆盖自身时不会变为不透明。
- 小块蒙版、着色图和临时图使用 `willReadFrequently: true`，降低高频小图羽化的 GPU 路径峰值；主画布及已提交文档瓦片沿用正常加速方式。
- 抬笔提交复用已有增量覆盖图；完成后释放实时蒙版。组件卸载也释放当前笔画的临时资源。

**外观兼容范围：** 新笔画持久化 `renderVersion: 2`，使用只依赖当前及过去采样的平滑/宽度计算；旧笔画继续使用旧版双向平滑与重采样算法。新笔画的局部宽度过渡可能和旧算法略有差别，不能宣称笔刷算法完全未变。版本字段确保新笔画提交、撤销重建、保存后重新打开时保持一致。旧格式铅笔和自由橡皮的绘制算法保留；新铅笔使用下述增量纹理。

### 密集笔画擦除

新增 `InkRasterCache.ts` 和 `InkStrokeIndex.ts`：

- 笔画正常提交或文档重建时，缓存每条笔画在各文档瓦片中的已着色、已羽化图像。缓存按实际包围盒裁剪，采用全局 64 MiB LRU 上限。
- 擦除后按原文档顺序合成附近幸存笔画的缓存图像，避免再次平滑、生成路径及羽化。缓存未命中时才重建对应笔画图像。
- 顺序重放包含 `destination-out` 自由橡皮擦痕，避免删除其他笔画后恢复已擦掉的墨迹。
- 继续使用可复用的整瓦片临时缓冲，只回填删除区域的像素，保留区域外的墨迹。图像生成和局部修复各有一个临时瓦片，3 倍采样下合计约 18 MiB，另计入当前笔画的小块缓冲。
- 空间索引随笔画提交、删除和文档重建维护。512 单位网格服务瓦片重放，64 单位网格缩小命中候选；每 32 个原始线段保存一个包围盒，长笔画只扫描可能命中的线段块。
- 点击仍只删最上层命中笔画；拖动按帧合并、抬笔一次提交历史。修正了反向擦除扫掠时包围盒扩展顺序的问题。

## 浏览器负载验证

独立无窗口 Edge 152.0.4191.66，Ryzen 7 7840H。旧版对照为本轮修改前的源码快照；不是最早版本。以下是合成负载的绘制/修复函数耗时，包含一个像素的同步读回，**不是 Electron 实机笔尖到屏幕的端到端延迟**。

### 连续左右往返

8 单位笔宽、50% 透明度、羽化开启，往返范围 40–520 世界单位，每帧新增 4 点。前缀初始化在计时外；每种配置最多测 6 帧，旧算法单帧超过 1 秒时停止该配置，防止压力测试长时间阻塞。

| 已累积点数 | 修改前 | 修改后中位耗时 | 修改后最慢样本 |
| --- | ---: | ---: | ---: |
| 512 | 39.7 ms，中位数 | 3.2 ms | 6.5 ms |
| 4,096 | 2,021.9 ms，单次观测 | 3.6 ms | 6.0 ms |
| 16,384 | 32,552.6 ms，单次观测 | 3.7 ms | 7.7 ms |

后两行旧算法只有一个样本，不能当作稳定中位数或实机典型耗时。每次追加 4 点，新算法均只处理 4 个新增点，刷新 2 个小块。

另从空笔画开始逐帧加入采样，连续运行 1,024 帧，共 4,096 点，避免只测试预先建立好的长前缀：

| 连续输入区间 | 每帧中位耗时 | P95 | 最慢样本 |
| --- | ---: | ---: | ---: |
| 点数 1–1,024 | 2.9 ms | 3.7 ms | 53.1 ms |
| 点数 1,025–2,048 | 2.9 ms | 4.0 ms | 5.1 ms |
| 点数 2,049–3,072 | 2.8 ms | 3.8 ms | 4.1 ms |
| 点数 3,073–4,096 | 2.9 ms | 3.6 ms | 4.1 ms |

唯一超过 16.67 ms 的样本出现在第 0 帧：绘制命令耗时 4.0 ms，同步读回耗时 49.1 ms。应用正常书写不执行这个测试用读回。该拆分说明不能将此峰值直接解释为用户实际掉了相同数量的帧，也不等于已经验证了端到端零卡顿。

## 实机复测与仍有的成本

当前用户使用开发版。刷新或重新启动开发窗口后，用默认标记笔保持按下连续往返，再在密集笔画上使用“橡皮 → 擦除笔画”。无限画布与 PDF 标注均已接入；核对抬笔前后外观、撤销/重做、透明度和之前的自由擦痕。

开发控制台的 `[eraser:canvas]` / `[eraser:pdf]` 日志中，`worstScan` 记录拖动命中检测，`worstRestamp` 记录一次局部修复批次，可以用于进一步区分实机成本。

本次消除了固定区域持续往返时反复处理整条历史路径的原因。实时开销仍与新增采样数量和当前笔画覆盖的空间面积有关；主画布仍需合成可见文档瓦片/PDF 背景。64 MiB 图像缓存被大量大笔画挤出后，擦除可能需要重新生成图像。旧格式的极长笔画首次加载或缓存未命中时仍使用旧算法。尚未采集用户 Electron 窗口的真实输入到显示轨迹，不能保证所有设备、笔刷及任意文档密度完全无延迟。


## 铅笔补齐记录（2026-09-11）

用户复测确认默认标记笔和钢笔已经流畅，但铅笔仍卡。原因是上一轮两个画布创建笔画时都明确排除了 pencil，没有设置它的增量渲染版本。旧的 `drawPencil` 每帧仍重建整个笔芯，并在 `drawPencilGrain` 中重新计算全程弧长、从头运行随机序列、生成全量铅痕路径。纹理成本随同一笔的长度持续增加。

现已将两个编辑器的新铅笔笔画也接入 `renderVersion: 2`：

- 笔芯使用独立的窄铅芯压感规则（0.28–0.70 倍笔宽，带最小宽度），累计覆盖后统一应用 0.85 倍设置透明度与羽化。
- `StreamingPencilGrain.ts` 沿新增路程生成短线状铅痕，以笔画 ID 与候选位置确定随机结果；不用每帧重新遍历整条笔画。只保留末尾尚未远离笔尖的少量候选，已完成纹理烘焙到独立的小块蒙版。
- 纹理透明度单独按 0.16 倍设置透明度合成。笔芯和纹理分别累计覆盖，反复描线不会由于重复提交透明图层而变成不透明。
- 原始实时笔尖的纹理只作临时预览，不推进随机位置或永久写入蒙版；后续采样确定后才烘焙。由此保持分批输入、抬笔提交、撤销重建、保存重载的一致性。
- 短铅痕可以长于一个很小的原始采样间距，避免慢写时退化为一串细点；长度与偏移限制在笔画包围盒内，起止笔尖保留无颗粒区域。
- 已提交的铅笔图像也进入同一个有内存上限的擦除缓存。旧铅笔数据继续使用旧版纹理，新版的平滑和颗粒位置与旧版不逐像素相同，保留的是窄笔芯、压感、短铅痕及透明度特征。

### 铅笔基准

同一隔离 Edge 浏览器、8 单位笔宽、50% 透明度、羽化开启，每帧追加 4 个左右往返采样点。原始数据见 [ink-pencil-default.json](ink-pencil-default.json)。

| 前缀长度 | 修改前 | 修改后中位耗时 | 修改后最慢样本 |
| --- | ---: | ---: | ---: |
| 512 点 | 40.6 ms，中位数 | 7.2 ms | 9.0 ms |
| 4,096 点 | 2,060.5 ms，单次观测 | 7.2 ms | 8.6 ms |

旧算法超过 1 秒后停止该配置，因此第二行只有单次旧版观测。前缀构建在计时外，包含同步像素读回。

| 累积到的点数 | 每帧中位耗时 | P95 | 最慢样本 |
| --- | ---: | ---: | ---: |
| 1,024 | 3.4 ms | 4.3 ms | 12.8 ms |
| 2,048 | 3.3 ms | 3.8 ms | 4.5 ms |
| 3,072 | 3.3 ms | 3.9 ms | 4.6 ms |
| 4,096 | 3.4 ms | 4.0 ms | 4.5 ms |
